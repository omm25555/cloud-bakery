# กฎโปรเจกต์ Cloud Bakery (ฉบับเต็ม)

## หลักการสูงสุด
1. ตรวจสอบทุกอย่าง ห้ามมีข้อผิดพลาด งานที่ยังไม่ผ่านการตรวจถือว่ายังไม่เสร็จ
2. งานที่ merge แล้วถือว่าล็อก ห้ามแก้ถ้า TASK ไม่ได้สั่งไว้ชัดเจน
3. ผู้เล่นต้องไม่งง ทุกการกระทำต้องมีผลตอบกลับที่ชัดเจน ทั้งตอนสำเร็จและไม่สำเร็จ
4. คุยให้ลงตัวก่อนลงมือ จุดไหนไม่ชัดให้ถามก่อนเขียนโค้ด ห้ามเดา
5. เซิร์ฟเวอร์เป็นผู้ตัดสิน ไคลเอนต์แค่ขอและแสดงผล

## บทบาท
- **Chaloemchai (เจ้าของ)**: ตัดสินใจเรื่องขอบเขต ดีไซน์ เงิน การเปิดตัว ทดสอบใน Studio และ merge
- **ผู้จัดการ Dev**: เขียน TASK รีวิว PR ตอบคำถามเทคนิค ไม่ merge ไม่ approve ไม่ push
- **Claude**: เขียนโค้ดตาม TASK ตรวจงานเอง เปิด PR ไม่ merge PR ของตัวเอง

## วงจรงาน
เปิด Issue แล้ว Claude ถามจุดไม่ชัด เมื่อตกลงกันแล้วจึงเขียนโค้ดและตรวจเอง จากนั้นเปิด PR พร้อมรายงานการตรวจ ผู้จัดการรีวิว แล้วเจ้าของทดสอบใน Studio และ merge
- branch `task-XXX-ชื่อสั้น` / PR ชื่อ `TASK-XXX: ...` / ใส่ `Closes #N` / หนึ่ง PR ต่อหนึ่ง TASK

## มาตรฐานโค้ด
- ทุกไฟล์ขึ้นต้นด้วย `--!strict` ไม่มี type error/warning ห้ามใช้ `::any` เพื่อหลบ type
- Service (server) / Controller (client) ตั้งชื่อแบบ PascalCase
- ตัวเลขทุกตัวอยู่ใน `shared/Config`
- require/path ตรงกับ `default.project.json` จัดการ nil ทุกจุด
- ห้ามมี TODO, print ทดสอบ หรือโค้ดที่ปิดคอมเมนต์ไว้
- ตัดการเชื่อมต่อ event เมื่อผู้เล่นออก

## ความปลอดภัยฝั่งเซิร์ฟเวอร์
- เหรียญ ไอเท็ม รางวัล ตัวจับเวลา และผลมินิเกม คำนวณที่เซิร์ฟเวอร์เท่านั้น
- ทุก remote ต้องเช็กชนิดข้อมูล ช่วงค่า และสิทธิ์ และต้องมี rate limit
- ผลมินิเกมต้องตรวจความเป็นไปได้ (เวลากับคะแนนต้องสมเหตุสมผล)
- DataStore ลองใหม่เมื่อล้มเหลว บันทึกตอนผู้เล่นออกและตอน BindToClose ข้อมูลห้ามหาย

## ระบบแจ้งเตือนและ log
| สถานการณ์ | ผู้เล่นเห็น | dev เห็น |
|---|---|---|
| สำเร็จ | ข้อความหรือเอฟเฟกต์สั้น ๆ | - |
| เงื่อนไขไม่ครบ | บอกเหตุผลและสิ่งที่ต้องทำ | - |
| เซิร์ฟเวอร์ปฏิเสธ | ข้อความสุภาพว่าทำไม่ได้ตอนนี้ | `warn` + ผู้เล่น + เหตุผล |
| บันทึกล้มเหลว | แจ้งว่ากำลังลองใหม่ | `warn` ทุกครั้งที่ลอง, `error` เมื่อล้มเหลวครบ |
| ข้อผิดพลาดไม่คาดคิด | ข้อความกลาง ๆ เกมต้องไม่ค้าง | `error` พร้อมที่มา |

ใช้ระบบแจ้งเตือนกลางระบบเดียว และให้ log ขึ้นต้นด้วยชื่อ Service เช่น `[BakeService]`

## งานที่ล็อกแล้ว
ถ้าจำเป็นต้องแก้ ให้หยุด แล้วคอมเมนต์บอกว่าจะแก้ไฟล์ไหน ทำไม และกระทบอะไร รอตกลงก่อน แล้วระบุไว้ใน PR ถ้าแก้โดยไม่ตกลงกันก่อน จะถูกสั่งให้ย้อนกลับ

## เกณฑ์ว่างานเสร็จ
- ครบทุกข้อใน Acceptance Criteria และ Rojo build ผ่าน ไม่มี type error
- ไม่แตะไฟล์นอกขอบเขตหรืองานที่ล็อก
- มีแจ้งเตือนผู้เล่นครบทุกกรณี และตัวเลขใหม่อยู่ใน Config
- PR มีรายงานการตรวจ และขั้นตอนทดสอบใน Studio ทีละข้อ
- อัปเดต `docs/` ถ้าระบบหรือตัวเลขเปลี่ยน

## ระดับปัญหาในการรีวิว
- **ร้ายแรง** (ไคลเอนต์โกงได้ ข้อมูลหาย แก้งานที่ล็อก) และ **ต้องแก้** (type error ไม่มีแจ้งเตือน ตัวเลขลอย): ห้าม merge จนกว่าจะแก้
- **แนะนำ**: แก้ใน PR นี้หรือ TASK ถัดไปก็ได้

## การสื่อสาร
- คุยใน Issue/PR เท่านั้น หนึ่งคำถามต่อหนึ่งประเด็น พร้อมเสนอทางที่แนะนำ
- ตกลงกันได้แล้วให้สรุปเป็นข้อ ๆ ก่อนเขียนโค้ด ถ้าติดขัดให้รายงานทันที

## บั๊ก
เปิด Issue `BUG-XXX` บอกอาการ วิธีทำให้เกิดซ้ำ และสิ่งที่ควรเป็น บั๊กที่ทำให้ข้อมูลหายหรือโกงได้ต้องแก้ก่อนงานอื่น หนึ่ง PR ต่อหนึ่งบั๊ก ถ้า merge แล้วเกมพังให้ revert ก่อน

## การควบคุมคอมพิวเตอร์
Chaloemchai อาจให้ Claude ควบคุมคอมพิวเตอร์เพื่อทำงานใน Roblox Studio โดยมีกฎดังนี้
1. **ทุกอย่างต้องอยู่ใน repo**: สคริปต์ทั้งหมดเขียนเป็นไฟล์ใน repo แล้ว sync ผ่าน Rojo จากนั้น commit ขึ้น GitHub ห้ามแก้สคริปต์ใน Studio ตรง ๆ โดยไม่ sync กลับ
2. **งานที่ทำใน Studio เท่านั้นต้องรายงาน**: เช่น สร้างโมเดล จัดฉาก หรือตั้งค่าใน Studio ให้คอมเมนต์ใน Issue ของ TASK นั้นว่าทำอะไรไปบ้าง พร้อมแนบภาพหน้าจอ และถ้าทำได้ให้ export เป็นไฟล์ `.rbxm` ไว้ใน repo
3. **อยู่ในขอบเขตโปรเจกต์**: ห้ามแตะไฟล์ โปรแกรม หรือบัญชีอื่นในเครื่องที่ไม่เกี่ยวกับโปรเจกต์ ห้ามติดตั้งโปรแกรม ห้าม publish เกม และห้ามเปลี่ยนการตั้งค่าเกมบน Roblox โดยที่ Chaloemchai ยังไม่อนุญาต
4. **รายงานความคืบหน้า**: เมื่อจบแต่ละช่วงงาน ให้คอมเมนต์สรุปใน Issue ว่าทำอะไรเสร็จแล้ว และยังเหลืออะไร เพื่อให้ผู้จัดการติดตามงานได้
